**Research findings:**
- 16 'any' types: 9 in integrity.ts, 1 in responses.ts, 6 in queries.ts
- Manual field mapping (snake_case ↔ camelCase) repeated in 5 query functions
- Dynamic table access requires 'as any' due to Supabase TS limitations
- JSONB fields need runtime casting

**Type safety issues:**
1. `lib/validators/integrity.ts`: Field comparison using `any` for flexibility
2. `lib/schemas/responses.ts`: Validation function accepts `any` data
3. `lib/supabase/queries.ts`: JSONB assertions and dynamic table routing use `any`

**Strategy:**
- Replace `any` with `unknown` where input type is truly unknown
- Use type unions for known variants (table names)
- Extract field mapping to eliminate repetition
- Use generics with proper constraints
</context>

  <action>
Create lib/supabase/mappers.ts with generic field mapping utilities to eliminate manual snake_case ↔ camelCase conversion.

Utilities to implement:

1. Type definitions:
   ```typescript
   export type FieldMap<TSource = Record<string, unknown>, TTarget = Record<string, unknown>> = {
     [K in keyof TTarget]?: keyof TSource
   }

   type CamelCase<S extends string> = S extends `${infer P1}_${infer P2}${infer P3}`
     ? `${P1}${Uppercase<P2>}${CamelCase<P3>}`
     : S

   type SnakeCase<S extends string> = S extends `${infer T}${infer U}`
     ? `${T extends Capitalize<T> ? '_' : ''}${Lowercase<T>}${SnakeCase<U>}`
     : S
   ```

2. **mapDbToApp<TDb, TApp>(dbRow: TDb, fieldMap?: FieldMap<TDb, TApp>): TApp**
   - Converts snake_case DB row to camelCase app object
   - If fieldMap provided, use explicit mapping
   - Otherwise, auto-convert snake_case → camelCase
   - Handle null/undefined fields
   - Preserve JSONB fields as-is (objects/arrays don't need case conversion)

3. **mapAppToDb<TApp, TDb>(appObj: TApp, fieldMap?: FieldMap<TApp, TDb>): TDb**
   - Converts camelCase app object to snake_case DB row
   - Reverse of mapDbToApp

4. **camelToSnake(str: string): string**
   - Helper: converts 'relatedSkills' → 'related_skills'
   - Handle acronyms carefully (ID, URL should become 'id', 'url')

5. **snakeToCamel(str: string): string**
   - Helper: converts 'related_skills' → 'relatedSkills'

6. **assertJson<T>(value: unknown): T | undefined**
   - Move from queries.ts to here for reuse
   - Type guard for JSONB fields
   - Returns undefined if value is null/undefined
   - Otherwise casts to T

Implementation notes:
- Use TypeScript generics with Record constraints
- Handle edge cases: null values, nested objects, arrays
- Export all functions
- Add JSDoc with usage examples

Example usage (add to JSDoc):
```typescript
// Automatic conversion
const skill: Skill = mapDbToApp<SkillRow, Skill>(dbRow)

// Explicit field mapping
const milestone: Milestone = mapDbToApp<MilestoneRow, Milestone>(dbRow, {
  displayName: 'display_name',
  relatedSkills: 'related_skills',
  // ... other mappings
})
```

This eliminates the repeated mapping logic in all 5 query functions.

Refactor lib/supabase/queries.ts to use generic field mapper, eliminating manual field mapping and 'any' types.

Steps:

1. Add import:
   ```typescript
   import { mapDbToApp, assertJson } from './mappers'
   ```

2. Remove local assertJson function (now imported from mappers)

3. Refactor each query function to use mapDbToApp:

   **fetchSkills example:**
   ```typescript
   // OLD (lines 49-57)
   const skills: Skill[] = (data || []).map((row: Database['public']['Tables']['skills']['Row']) => ({
     id: row.id,
     name: row.name,
     level: row.level,
     description: row.description,
     category: row.category,
     type: row.type as 'hard' | 'soft',
     requirements: assertJson<SkillRequirement[]>(row.requirements)
   }))

   // NEW
   const skills: Skill[] = (data || []).map((row) => {
     const mapped = mapDbToApp<typeof row, Skill>(row)
     return {
       ...mapped,
       type: row.type as 'hard' | 'soft',
       requirements: assertJson<SkillRequirement[]>(row.requirements)
     }
   })
   ```

   For fields that already match (id, name, level, etc.), mapDbToApp handles them.

  <name>Task 3: Eliminate 'any' types in integrity validator</name>
  <files>lib/validators/integrity.ts</files>
  <action>
Refactor lib/validators/integrity.ts to eliminate 9 'any' types using proper type constraints.

Current 'any' usage:
- `mockValue?: any` → replace with `unknown`
- `dbValue?: any` → replace with `unknown`
- `find((db: any) => ...)` → replace with proper array type
- `compareFields(mockItem: any, dbItem: any)` → replace with `Record<string, unknown>`
- `mockData: any, dbData: any` → replace with generic constraints

Refactoring strategy:

1. Replace IntegrityMismatch interface:
   ```typescript
   // OLD
   interface IntegrityMismatch {
     field: string
     mockValue?: any
     dbValue?: any
   }

   // NEW
   interface IntegrityMismatch {
     field: string
     mockValue?: unknown
     dbValue?: unknown
   }
   ```

2. Make compareFields generic:
   ```typescript
   // OLD
   function compareFields(mockItem: any, dbItem: any): IntegrityMismatch[]

   // NEW
   function compareFields<T extends Record<string, unknown>>(
     mockItem: T,
     dbItem: T
   ): IntegrityMismatch[]
   ```

3. Make compareData generic:
   ```typescript
   // OLD
   function compareData(
     entity: string,
     mockData: any,
     dbData: any,
     idField = 'id'
   ): IntegrityResult

   // NEW
   function compareData<T extends Record<string, unknown> & { id: string }>(
     entity: string,
     mockData: T[],
     dbData: T[],
     idField: keyof T = 'id'
   ): IntegrityResult
   ```

4. Replace array find type assertions:
   ```typescript
   // OLD
   const dbItem = dbArray.find((db: any) => db.id === mockItem.id)

   // NEW
   const dbItem = dbArray.find((db) => db[idField] === mockItem[idField])
   ```

5. Update fetchFromDb return type:
   ```typescript
   // OLD
   async function fetchFromDb(entity: string): Promise<{ data: any; error: string | null }>

   // NEW
   async function fetchFromDb(entity: string): Promise<{ data: Record<string, unknown>[]; error: string | null }>
   ```

6. Expected outcome:
   - 9 'any' types → 0 'any' types
   - 'unknown' used for truly unknown data
   - Generics with Record constraints for structured data
   - Type safety improved without breaking functionality

Preserve all validation logic, comparison algorithms, error detection.
